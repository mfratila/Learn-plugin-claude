The mental model

SESSION 1

Five facts that most of this sheet follows from. When a command surprises you, check which of these it comes from.

T1 · architectureAutomation is commands sent to a browser over a protocol.Playwright keeps one persistent two-way connection open, while classic WebDriver sends one HTTP request per command. Because the browser can send messages first, Playwright gets events, page.route() interception and fast auto-waiting.
T2 · the raceThe page changes on its own schedule, not yours.So locators are recipes resolved again on each use, actions auto-wait, and assertions retry.
T3 · isolationA test is trustworthy only if it depends on nothing but the app.So every test gets a fresh BrowserContext (an incognito-like profile). The browser process is shared.
T4 · typesTypeScript types are erased at runtime.Types catch mistakes while you write code. They never check real data, such as an API response, while the test runs.
HierarchyBrowser → BrowserContext → PageOne browser per worker → one context per test → one or more pages (tabs) per context.

CLI: the commands you'll type daily

SESSION 1

The equivalent of the git cheat sheet. Everything goes through npx playwright. The test runner is part of the package, so there's no separate CLI to install.

npm init playwright@latest

Start a new project. Creates the config, an example test, and optionally a GitHub Actions workflow. It also installs the browsers.

npx playwright install --with-deps chromium

Install browsers and their OS dependencies. Leave out chromium to install all three. Used on fresh machines and in CI.

npx playwright test

Run everything, headless and in parallel, using playwright.config.ts.

npx playwright test tests/login.spec.ts:12

Run one file, or just the test on line 12.

npx playwright test -g "checkout"
npx playwright test --grep @smoke

Filter by title or tag. --grep-invert excludes matches instead.

npx playwright test --project=chromium

Run one project (a browser, device, or environment defined in the config).

npx playwright test --ui

UI mode. Watch mode, a time-travel DOM view, and picking tests to run. Your main tool while writing tests.

npx playwright test --headed --workers=1

Watch it run in a visible browser, one test at a time.

npx playwright test --debug

Step through with the Playwright Inspector, which pauses before every action.

npx playwright test --last-failed

Re-run only the tests that failed last time.

npx playwright test --repeat-each=10

Hunt for flakiness. Runs each test 10 times. A test that fails only sometimes is flaky.

npx playwright test --list

List the tests that would run, without running them. Handy for checking grep and project filters.

npx playwright show-report

Open the HTML report from the last run.

npx playwright show-trace trace.zip

Open a trace, for example one downloaded from CI. It shows every action with DOM snapshots, network, and console.

npx playwright codegen localhost:3200

Record actions into code. Use it to find good locators, not to write whole tests.

npx playwright test --update-snapshots

Re-record visual baselines after an intended UI change. COMING UP

npx playwright test --shard=1/4

Run a quarter of the suite. Used to split work across CI machines. COMING UP

npx playwright test --only-changed=main

Run only the tests affected by your git changes since main. Gives a fast first signal in CI. COMING UP

Test structure

SESSION 1

Close to Mocha/Jasmine, which you know from WDIO. The difference: setup is requested by name in { page, ... } (fixtures) and not set up through shared variables.

import { test, expect } from '@playwright/test';

test('user can log in', async ({ page }) => {
  await page.goto('/login');
  // ...
});

The basic test. { page } is a fixture: a fresh page in a fresh context, created for this test only.

test.describe('checkout', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/shop');
  });
  test('adds item', async ({ page }) => { /*...*/ });
});

Grouping and hooks. Fine for simple navigation. For reusable setup, prefer fixtures.

await test.step('fill shipping address', async () => {
  // several actions
});

Named steps show up as collapsible blocks in reports and traces. They make long tests readable.

for (const path of ['/stages', '/dashboard', '/labs']) {
  test(`${path} redirects anonymous users to login`, async ({ page }) => {
    await page.goto(path);
    await expect(page).toHaveURL('/login');
  });
}

Data-driven tests. Put the loop outside test() so each case is its own test, with its own result, run in parallel. Titles must be unique.

// test.step = phases of ONE behaviour
// test()    = ONE behaviour; a failure stops it

Step or test? If a failure in one part shouldn't hide the result of another, they're separate behaviours, so make them separate tests.

test('pays', { tag: ['@smoke', '@checkout'] }, async ({ page }) => {});

Tags, which you select with --grep @smoke.

test.skip(isMobile, 'no hover on mobile');
test.fixme('known bug #123');
test.slow();   // triples the timeout

Annotations. Skip with a reason, mark a known-broken test, or allow more time.

test.use({ viewport: { width: 390, height: 844 } });

Override options for one file or describe block, such as viewport, locale or storageState.

Locators

SESSION 1

From T2: a locator is a recipe, resolved again on every action or assertion. Creating one needs no await. It's strict: a single-target operation on several matches throws. Prefer what the user sees: role, then label or text, then test id, then CSS as a last resort.

page.getByRole('button', { name: 'Save' })
page.getByRole('heading', { name: 'Dashboard', level: 1 })
page.getByRole('link', { name: 'Docs', exact: true })

First choice. Matches the accessibility role and accessible name, the way a user or screen reader sees the page.

page.getByLabel('Email')
page.getByPlaceholder('you@example.com')

Form fields, found by their label or placeholder.

page.getByText('Order placed')
page.getByText(/total: \$\d+/i)

Non-interactive text. Matches substrings by default. Pass exact: true or a regex to be precise.

page.getByTestId('cart-count')

A stable contract with developers, using data-testid by default. Change the attribute with testIdAttribute in the config.

page.locator('#legacy .price')
page.locator('xpath=//td[3]')

CSS or XPath, as a last resort. These break when markup changes, even if the user sees the same page.

page.getByRole('row', { name: 'Order 42' })
    .getByRole('button', { name: 'Delete' })

Chaining narrows the scope. This is the standard fix for a strict mode violation.

page.getByRole('listitem')
    .filter({ hasText: 'Laptop' })
    .filter({ has: page.getByRole('button', { name: 'Buy' }) })

Filter by text or by a child element. hasNot and hasNotText exclude instead.

items.first()   items.last()   items.nth(2)
await items.count()
for (const item of await items.all()) { /*...*/ }

When you mean one of many, say so explicitly. count() and all() work on the whole set, so strictness doesn't apply.

saveBtn.or(confirmDialog)
page.getByRole('button').and(page.getByTitle('Close'))

Combine recipes. or matches either one (e.g. "whichever appears first"). and requires both.

page.frameLocator('#payment').getByLabel('Card number')

Inside an iframe. No switchToFrame: you scope the locator to the frame instead.

Actions

SESSION 1

From T2: every action auto-waits until the checks it needs pass (Visible, Stable, Receives Events, Enabled, Editable), and fails only if they're still failing when the timeout runs out. Always await actions.

await page.goto('/login');

Navigate. Relative paths resolve against baseURL from the config.

await btn.click();
await btn.dblclick();
await btn.click({ button: 'right' });

Click. Waits for Visible, Stable, Receives Events and Enabled.

await page.getByLabel('Email').fill('qa@test.dev');
await input.clear();

Set a field's value in one go, like WDIO setValue. Waits for Visible, Enabled and Editable.

await input.pressSequentially('laptop', { delay: 50 });

Type key by key, for inputs that react to each keystroke (autocomplete). type() is deprecated.

await input.press('Enter');
await page.keyboard.press('Control+A');

Keys and shortcuts.

await checkbox.check();
await checkbox.setChecked(false);
await select.selectOption({ label: 'Blue' });

Checkboxes, radios and selects. They ensure the final state, so check() on an already-checked box does nothing.

await page.getByLabel('Upload').setInputFiles('fixtures/cv.pdf');

File upload. Sets the file directly, with no OS dialog.

await card.hover();
await item.dragTo(page.getByTestId('bin'));

Hover and drag.

page.once('dialog', d => d.accept());
await deleteBtn.click();

Native alert and confirm dialogs. Register the handler before the click that opens the dialog.

await spinner.waitFor({ state: 'hidden' });

Explicit wait for a state. Rarely needed, because actions and assertions already wait.

const total = await page.evaluate(() => window.cart.total);

Run JavaScript in the page, like WDIO browser.execute.

await page.screenshot({ path: 'shot.png', fullPage: true });

Manual screenshot. Usually you'd let the config capture them on failure.

Web-first assertions

SESSION 1

The rule: a locator inside expect() plus await in front means it retries (default 5 s). A value inside expect() is a snapshot and is checked once.

await expect(toast).toBeVisible();
await expect(spinner).toBeHidden();

Presence. toBeAttached() checks the element is in the DOM, whether or not it's visible.

await expect(status).toHaveText('Paid');
await expect(status).toContainText('Pai');
await expect(rows).toHaveText(['A', 'B', 'C']);

Text. toHaveText matches the whole text (or a regex). An array checks every match, in order.

await expect(rows).toHaveCount(3);

Count. The retrying replacement for expect(await rows.count()).

await expect(input).toHaveValue('qa@test.dev');
await expect(box).toBeChecked();
await expect(btn).toBeEnabled();   // / toBeDisabled()
await expect(input).toBeFocused();

Form state.

await expect(link).toHaveAttribute('href', /\/orders\/\d+/);
await expect(tab).toHaveClass(/active/);

Attributes and classes.

await expect(page).toHaveURL(/\/dashboard/);
await expect(page).toHaveTitle('QA Learning App');

Page-level checks. Note it's expect(page), not a locator.

await expect(res).toBeOK();   // API response: 2xx

API responses from the request fixture. COMING UP

await expect.soft(price).toHaveText('$10');
await expect.soft(tax).toHaveText('$2');

Soft assertions. Failures are recorded but the test keeps going, so you see every mismatch in one run.

await expect.poll(async () => {
  const r = await request.get('/api/orders/42');
  return (await r.json()).status;
}, { timeout: 10_000 }).toBe('PAID');

Retry anything that isn't a locator, such as an API value or a database row. COMING UP

await expect(async () => {
  await page.reload();
  await expect(badge).toHaveText('3');
}).toPass({ timeout: 15_000 });

Retry a whole block until every check in it passes. COMING UP

await expect(page).toHaveScreenshot();
await expect(nav).toMatchAriaSnapshot(`
  - link "Dashboard"
  - link "Labs"`);

Visual and accessibility-tree snapshots. COMING UP

Browsers, contexts, pages

SESSION 1

From T3: each test gets a fresh context with its own cookies and storage, at almost no cost. You can also open more contexts yourself for multi-user scenarios.

test('admin approves, customer sees it', async ({ page, browser }) => {
  const adminCtx = await browser.newContext({ storageState: 'auth/admin.json' });
  const admin = await adminCtx.newPage();
  // page = customer, admin = admin, fully isolated
  await adminCtx.close();
});

Two users in one test. Two isolated contexts inside one browser process.

const popupPromise = page.waitForEvent('popup');
await page.getByText('Open invoice').click();
const popup = await popupPromise;

New tab or popup. Start waiting before the click that opens it. context.waitForEvent('page') catches any new page.

await context.storageState({ path: 'auth/user.json' });
test.use({ storageState: 'auth/user.json' });

Save and reuse a login, so you log in once rather than in every test. COMING UP

await context.addCookies([{ name: 'consent', value: 'no', url: 'http://localhost:3200' }]);
await context.grantPermissions(['geolocation']);

Shape the context's state before the test acts.

Fixtures

SESSION 1

Setup, await use(value) and teardown in one function. A fixture runs only when a test asks for it by name, can depend on other fixtures, and is typed. This is how the industry standard POM via fixtures works.

// fixtures.ts
import { test as base } from '@playwright/test';
import { LoginPage } from './pages/LoginPage';

export const test = base.extend<{ loginPage: LoginPage }>({
  loginPage: async ({ page }, use) => {
    const lp = new LoginPage(page);   // setup
    await use(lp);                    // test runs here
                                      // teardown after use()
  },
});
export { expect } from '@playwright/test';

A custom test-scoped fixture. Tests import test from your fixtures file, not from @playwright/test.

import { test, expect } from './fixtures';

test('rejects bad password', async ({ loginPage }) => {
  await loginPage.login('qa@test.dev', 'wrong');
  await expect(loginPage.error).toBeVisible();
});

Using it. Ask for it by name and it's created for you. Tests that don't ask for it never pay its cost.

export const test = base.extend<{}, { apiToken: string }>({
  apiToken: [async ({}, use) => {
    await use(await fetchToken());
  }, { scope: 'worker' }],
});

Worker-scoped: set up once per worker process, for expensive things. Note the second type parameter. COMING UP

failOnConsoleErrors: [async ({ page }, use) => {
  const errors: string[] = [];
  page.on('console', m => m.type() === 'error' && errors.push(m.text()));
  await use();
  expect(errors).toEqual([]);
}, { auto: true }],

Auto fixtures run for every test without being requested. Good for cross-cutting checks. COMING UP

import { mergeTests } from '@playwright/test';
export const test = mergeTests(pagesTest, apiTest);

Combine fixture files as the framework grows. COMING UP

playwright.config.ts

COMING UP

This replaces wdio.conf.js. It holds runner settings at the top level, browser and context options in use, and variants in projects.

import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,                       // parallelise tests inside files too
  forbidOnly: !!process.env.CI,              // fail CI if a test.only slipped in
  retries: process.env.CI ? 2 : 0,           // pass-on-retry ⇒ reported as "flaky"
  workers: process.env.CI ? 1 : undefined,
  reporter: [['html'], ['list']],
  timeout: 30_000,                           // per test
  expect: { timeout: 5_000 },                // per web-first assertion
  use: {
    baseURL: process.env.BASE_URL ?? 'http://localhost:3200',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
  },
  projects: [
    { name: 'setup', testMatch: /.*\.setup\.ts/ },
    { name: 'chromium', use: { ...devices['Desktop Chrome'], storageState: 'auth/user.json' }, dependencies: ['setup'] },
    { name: 'mobile',   use: { ...devices['Pixel 7'] } },
  ],
  webServer: {
    command: 'pnpm dev',
    url: 'http://localhost:3200',
    reuseExistingServer: !process.env.CI,
  },
});

A realistic starting config. A setup project logs in once and saves storageState, and the other projects depend on it. webServer starts the app before the tests run.

Debugging

SESSION 1

Thanks to the persistent connection (T1), Playwright can record everything: actions, DOM snapshots, network and console. Read the trace before you reach for console.log.

await page.pause();

Breakpoint. Opens the Inspector at this line when running headed or with --debug.

npx playwright test --ui

UI mode. Re-runs on save and lets you scrub through each step's DOM.

use: { trace: 'on-first-retry' }

The trace in CI. Recorded only when a test is retried, so it's cheap when everything passes and detailed when something fails.

page.on('console', m => console.log('[browser]', m.text()));
page.on('requestfailed', r => console.log('FAILED', r.url()));

Listen to browser events. Only possible because the browser can send messages first (T1).

Network & API

COMING UP

From T1: the browser can pause a request and ask the test what to do. That lets you fake backends, test error states, and set up data through the API instead of the UI.

await page.route('**/api/orders', route =>
  route.fulfill({ json: [{ id: 42, status: 'PAID' }] }));

Mock a response. Register the route before the page makes the request.

await page.route('**/api/orders', route =>
  route.fulfill({ status: 500 }));

Force an error state, which is hard to trigger against a real backend.

await page.route('**/*.{png,jpg}', r => r.abort());
await page.route('**/api/**', async route => {
  const res = await route.fetch();
  const json = await res.json();
  await route.fulfill({ response: res, json: { ...json, beta: true } });
});

Block or modify real responses.

const resP = page.waitForResponse(r =>
  r.url().includes('/api/orders') && r.status() === 201);
await page.getByRole('button', { name: 'Place order' }).click();
const res = await resP;

Wait for a specific response. Start waiting before the click, or a fast response can arrive before you're listening.

test('create order via API', async ({ request }) => {
  const res = await request.post('/api/orders', { data: { sku: 'LAPTOP' } });
  await expect(res).toBeOK();
  const body = await res.json();
});

API testing, and API-based setup for UI tests. Shares baseURL with the config.

Traps

TRAP

The first two caught you in Session 1, and the test-data and .entries() ones came up in your first hands-on suite. All of them come from habits that worked fine somewhere else.

// ✗ throws if 2 "Delete" buttons exist
await page.getByRole('button', { name: 'Delete' }).click();
// ✓ scope it, or say "first" on purpose
await row.getByRole('button', { name: 'Delete' }).click();

"First match wins" doesn't exist here. Ask yourself: does this operation only make sense for exactly one element?

// ✗ snapshot: never retries, despite the outer await
await expect(await status.textContent()).toBe('Paid');
// ✓ locator inside expect
await expect(status).toHaveText('Paid');

What decides whether it retries is what's inside expect(), not the await in front of it.

// ✗ floating promise: may never be checked
expect(status).toHaveText('Paid');

A missing await is the most common Playwright bug. Turn on the lint rules @typescript-eslint/no-floating-promises and playwright/missing-playwright-await.

// ✗ races the response
await btn.click();
await page.waitForResponse('**/api/orders');
// ✓ listen first, then act
const p = page.waitForResponse('**/api/orders');
await btn.click(); await p;

Start listening for an event before you trigger it. The same applies to popups, dialogs and downloads.

let orderId: string;   // ✗ set in test A, read in test B

Sharing state between tests breaks T3, and it breaks for real under fullyParallel. Create the data a test needs inside that test or its fixtures.

const order = (await res.json()) as Order;  // ✗ not a check

A type annotation doesn't validate anything (T4). To check an API's shape at runtime, validate it, for example with a schema library. COMING UP

// ✗ ~50% chance of a repeat after ~118 runs (birthday problem)
const email = `user${Math.floor(Math.random() * 10000)}@test.com`;
// ✓ effectively unique
const email = `qa-${crypto.randomUUID().slice(0, 8)}@test.com`;

"Probably unique" test data fails at random once the database fills up. Make uniqueness guaranteed.

// ✗ destructures each STRING: index='/', value='s'
for (const [index, value] of paths.values())
// ✓ entries() yields [index, value] pairs
for (const [index, value] of paths.entries())

.values() vs .entries(). Both type-check, because types catch mistakes in shape, not in meaning. Hover over the variable to see what it really is.

await page.waitForTimeout(3000);   // ✗

Fixed sleeps make tests both slow and flaky. Wait for a condition instead, with a web-first assertion or waitForResponse.
